The StoreRouter search endpoint returns results one page at a time. When more products match your query than fit on a single page, the response includes a `nextCursor` field you pass back to fetch the next page. This cursor-based model ensures you can iterate through a full result set consistently, even as the underlying catalog updates.

## How cursor-based pagination works

Each `POST /v1/products/search` response contains:

- `items` — the current page of products (up to `limit` items)
- `nextCursor` — a string token encoding the engine's continuation state, or `null` if you have reached the last page

To advance to the next page, send the same request again with the `nextCursor` value passed as `cursor`. Keep repeating until `nextCursor` is `null`.

<Warning>
  Cursors are opaque. Do not parse, decode, or construct them manually. Their internal format may change between API versions. Pass back exactly the `nextCursor` the previous page returned, with the same request body. A cursor that is malformed, was issued under a different cursor version, or no longer maps onto the current query returns `400` with `{"detail": "invalid cursor"}`. Restart from page 1 by omitting `cursor`.
</Warning>

<Note>
  Pages are consecutive slices of one ranked list, so they don't overlap. A search with `q` ranks a bounded set of products, so it ends after a limited number of pages. A product can still repeat if the catalog changes between requests, so de-duplicate by `uuid` when you concatenate pages.
</Note>

## The pagination pattern

<Steps>
  <Step title="Send your initial search request">
    Issue `POST /v1/products/search` with your filters and an optional `limit` (1–100, default 50). Do not include a `cursor` on the first request.
  </Step>
  <Step title="Check nextCursor in the response">
    If `nextCursor` is `null`, the response is the only (or last) page — you are done. If `nextCursor` is a non-null string, there are more results.
  </Step>
  <Step title="Send the next request with cursor">
    Repeat the same request, passing the `nextCursor` value as `cursor`. Keep the rest of the request body — including `catalogs`, `facets`, and `relax` if you sent them — identical to the original request.
  </Step>
  <Step title="Repeat until nextCursor is null">
    Continue sending requests until `nextCursor` is `null`. That response contains the final page of results.
  </Step>
</Steps>

## Complete pagination loop

The examples below collect all matching products into a list, de-duplicated by `uuid`. For large catalogs, consider processing each page as it arrives rather than accumulating everything in memory.

<CodeGroup>

```python python
import asyncio
from octogen_ai_sdk import OctogenClient
from octogen_ai_sdk.models import MerchantProductListItem

async def fetch_all_products(
    query: str,
) -> list[MerchantProductListItem]:
    by_uuid: dict[str, MerchantProductListItem] = {}

    async with OctogenClient(base_url="https://api.storerouter.ai/v1") as client:
        cursor: str | None = None

        while True:
            page = await client.search_products(
                q=query,
                cursor=cursor,
                limit=50,
            )
            for item in page.items:
                by_uuid.setdefault(item.uuid, item)  # the catalog can change between pages

            if page.next_cursor is None:
                break  # reached the last page
            cursor = page.next_cursor

    return list(by_uuid.values())


async def main() -> None:
    products = await fetch_all_products("hoodie")
    print(f"Total products fetched: {len(products)}")
    for product in products:
        print(f"- {product.title} ({product.product_url})")

asyncio.run(main())
```

```typescript typescript
import { OctogenClient } from "@octogen-ai/sdk";
import type { MerchantProductListItem } from "@octogen-ai/sdk";

async function fetchAllProducts(
  query: string,
): Promise<MerchantProductListItem[]> {
  const client = new OctogenClient({ baseUrl: "https://api.storerouter.ai/v1" });
  const byUuid = new Map<string, MerchantProductListItem>();
  let cursor: string | undefined;

  while (true) {
    const page = await client.searchProducts({
      q: query,
      cursor,
      limit: 50,
    });

    for (const item of page.items) {
      if (!byUuid.has(item.uuid)) byUuid.set(item.uuid, item); // the catalog can change between pages
    }

    if (page.nextCursor == null) {
      break; // reached the last page
    }
    cursor = page.nextCursor;
  }

  return [...byUuid.values()];
}

const products = await fetchAllProducts("hoodie");
console.log(`Total products fetched: ${products.length}`);
for (const product of products) {
  console.log(`- ${product.title ?? "Untitled"} (${product.productUrl})`);
}
```

</CodeGroup>

## The limit parameter

Set `limit` to control how many items the API returns per page. The valid range is 1–100 and the default is 50.

Smaller page sizes reduce response latency for interactive use cases. Larger page sizes reduce the total number of round trips for batch jobs. Keep `limit` consistent across pages: changing it mid-iteration does not cause an error, but it may produce unexpected page boundaries.

<Tip>
  For batch export jobs that process the entire catalog, `limit: 100` minimizes the number of API calls. For interactive search UIs where the user sees results one page at a time, `limit: 20` or `limit: 25` keeps each response fast.
</Tip>
